3 ОПИС ВИКОНАНОЇ РОБОТИ
3.1 Вступ
Рефакторинг дозволяє покращити структуру існуючого коду без зміни його зовнішньої поведінки. У цій доповіді розглядаються три методи рефакторингу програмного коду. Метод Replace Array with Object застосовується для перетворення масивів з індексованими даними на об'єкти з іменованими властивостями, що робить код самодокументованим. Метод Replace Exception with Test використовується для запобігання надмірного використання механізму винятків у випадках, коли можна заздалегідь перевірити можливість виникнення помилки.. Метод Replace Nested Conditional with Guard Clauses спрощує складні вкладені умови шляхом виділення всіх особливих випадків в окремі умовні оператори, які у випадках настання граничних умов будуть відразу закінчувати виконання і повертатимуть потрібне значення.


3.2 Метод Replace Array with Object
3.2.1 Опис проблеми 


У початковій версії коду функції реєстрації користувача дані зберігаються у масиві userData, де кожен елемент має числовий індекс.
Проблеми цього підходу:
* Неможливо зрозуміти призначення userData[2] без коментарів або перегляду ініціалізації масиву;
* Легко переплутати індекси (наприклад, використати userData[1] замість userData[2]);
* При додаванні нових полів можна порушити існуючу індексацію;
* При зміні порядку елементів у масиві потрібно оновлювати весь код;
* Додавання нових полів ускладнює читання коду;
* Неможливо використати сучасні можливості JavaScript (деструктуризація, spread-оператор);
* Новим розробникам важко зрозуміти логіку без детального вивчення.


Метод рефакторингу Replace Array with Object замінює масив з індексованими даними на об'єкт з іменованими властивостями, що забезпечує:
* Самодокументованість - назви властивостей пояснюють їх призначення;
* Безпеку - неможливо помилитися з іменами властивостей (IDE підкаже помилку);
* Гнучкість - легко додавати, видаляти або переставляти поля.


3.2.2 Код до рефакторингу 
        Оформлення програмного коду до рефакторингу Replace Array with Object можна побачити в Додаток В.1.
3.2.3 Пояснення обраного методу 
У нашому коді дані користувача зберігаються в масиві з числовими індексами, де кожен елемент має своє призначення: перший елемент - ім'я, другий - прізвище, третій - email тощо. Це неправильне використання масиву, оскільки масиви в JavaScript призначені для однорідних колекцій даних, таких як список товарів або масив чисел. Наші дані є структурою з різними полями, кожне з яких має своє унікальне призначення, і ми не виконуємо типові операції з масивами. 
Об'єкти в JavaScript створені саме для представлення сутностей та зберігання структурованих даних з іменованими властивостями. Метод Replace Array with Object точно відповідає природі наших даних - ми описуємо сутність "користувач" з фіксованим набором полів, де порядок цих полів не має значення для бізнес-логіки. Також ми можемо застосувати деструктуризацію об'єктів для витягування даних з req.body, використати shorthand syntax для створення об'єкта та spread operator для передачі даних у методи ORM. Все це робить код більш виразним і компактним.
Метод покращує читабельність коду миттєво. Порівняймо: при хешуванні паролю bcrypt.hash(userData[3], 10) змушує нас згадувати, що третій індекс це пароль, а bcrypt.hash(userData.password, 10) говорить сам за себе.


3.2.4 Переваги отриманого коду після застосування методу
        
        Після рефакторингу коду ми отримуємо програмний код, який можна побачити в Додаток В.2.
Застосування методу Replace Array with Object змінив код з незрозумілого набору індексів у структуру даних. Тепер кожне звернення до даних користувача є зрозумілим.


        Переваги:
* Код є самодокументованим та добре читається і не потребує коментарів для пояснення;
* userData.email замість userData[2] - одразу зрозуміло призначення поля;
* Перевірка валідації !first_name || !last_name зрозуміліша за !userData[0] || !userData[1];
* Неможливо випадково переплутати поля (email замість password);
* Зміна порядку властивостей не впливає на роботу коду;
* Додавання нового поля (наприклад, phone_number) не вимагає перенумерації індексів;
* Видалення поля не ламає решту коду;
* Використання можливостей JavaScript(Деструктуризація, Shorthand syntax, Spread operator).


3.3 Метод Replace Exception with Test
3.3.1 Опис проблеми 


У початковій версії коду функції додавання оцінки до рецепту використовується підхід з обробкою винятків для перевірки валідності даних та унікальності оцінки.
Проблеми цього підходу:
* Використання винятків для контролю нормальної бізнес-логіки є антипатерном;
* Винятки є ресурсоємними операціями;
* Код стає менш зрозумілим через нагромадження блоків try/catch;


3.3.2 Код до рефакторингу 
Оформлення програмного коду до рефакторингу Replace Exception with Test можна побачити в Додаток В.3.
3.3.3 Пояснення обраного методу 


Метод Replace Exception with Test замінює використання винятків для керування звичайною логікою програми на прості перевірки умов. Замість того, щоб спочатку виконувати дію й потім ловити помилку, ми перевіряємо, чи можна виконати цю дію заздалегідь.
У нашому випадку, замість:
* викидання винятку під час перевірки валідності оцінки;
* спроби створення запису й обробки помилки унікальності;
* обробки винятку, коли рецепт не знайдено;

ми використовуємо звичайні перевірки. Це дозволяє:
   * уникнути непотрібних винятків у нормальних ситуаціях;
   * зробити код простішим і зрозумілішим;
   * краще контролювати бізнес-логіку через явні умови;


3.3.4 Переваги отриманого коду після застосування методу


Після рефакторингу коду ми отримуємо програмний код, який можна побачити в Додаток В.4.


Переваги
   * Уникнуто непотрібних запитів до бази даних при виявленні конфліктів на ранніх етапах
   * Спрощено ланцюжок обробки помилок, що прискорило виконання успішних сценаріїв
   * Код тепер має лінійну структуру з чіткими умовними перевірками замість вкладених блоків try/catch
   * Умовні конструкції if (!recipe) та if (existingRating) однозначно описують бізнес-логіку
   * Видалено антипатерн використання винятків для керування звичайною логікою програми.

3.4 Метод Replace Nested Conditional with Guard Clauses
3.4.1 Опис проблеми 


У початковій версії коду функції додавання рецепту до улюблених використовуються глибоко вкладені умовні конструкції. Код містить чотири рівні вкладеності: перевірка автентифікації користувача, перевірка наявності recipe_id, перевірка існування рецепту в базі даних, та перевірка чи рецепт вже не доданий до улюблених.
Проблеми цього підходу:
   * Важко відстежувати логіку через множинні рівні вкладеності
   * Основна бізнес-логіка "захована" всередині останньої умови
   * Доводиться тримати в голові всі умови одночасно для розуміння коду
   * При додаванні нової перевірки потрібно створювати ще один рівень вкладеності
   * Важко знайти відповідні блоки else для кожного if
   * Незрозуміло, де закінчується одна перевірка і починається інша
   * Важко побачити всі можливі шляхи виконання функції
Метод рефакторингу Replace Nested Conditional with Guard Clauses замінює вкладені умови на послідовність перевірок на початку функції, що забезпечує:
   * Всі перевірки на одному рівні
   * Ранній вихід з функції при виявленні помилки
   * Зосередження основної логіки в кінці функції без вкладеності


3.4.2 Код до рефакторингу 
        Оформлення програмного коду до рефакторингу Replace Nested Conditional with Guard Clauses можна побачити в Додаток В.5.
3.4.3 Пояснення обраного методу 


У нашому коді функція додавання рецепту до улюблених містить чотири послідовні перевірки, кожна з яких створює новий рівень вкладеності. Ця структура ускладнює читання коду, оскільки основна бізнес-логіка створення запису у таблиці Favorites знаходиться всередині четвертого рівня вкладеності. Ми повинні прочитати весь код і відстежити всі умови, щоб зрозуміти, що відбувається у випадку успішного виконання.
Метод Replace Nested Conditional with Guard Clauses вирішує цю проблему шляхом переміщення всіх перевірок на початок функції. Замість перевірки позитивних умов та вкладення коду всередину блоків if, ми перевіряємо негативні умови та негайно виходимо з функції при їх виявленні.
Метод покращує читабельність коду миттєво. Замість чотирьох вкладених if-блоків з else-гілками, ми отримуємо лінійну послідовність перевірок, де кожна займає 3-4 рядки.  Основна логіка створення запису await Favorites.create({ user_id, recipe_id }) тепер знаходиться в кінці функції на нульовому рівні вкладеності, що робить її очевидною та легкою для знаходження.


3.4.4 Переваги отриманого коду після застосування методу


Після рефакторингу коду ми отримуємо програмний код, який можна побачити в Додаток В.6.
Застосування методу Replace Nested Conditional with Guard Clauses змінило код з глибоко вкладеної структури в лінійну послідовність перевірок. Тепер кожна умова знаходиться на одному рівні вкладеності, а основна бізнес-логіка чітко видна в кінці функції.
Переваги:
   * Код читається зверху вниз як послідовність кроків;
   * Не потрібно відстежувати множинні рівні вкладеності;
   * Основна логіка знаходиться в кінці без вкладень;
   * Кожна перевірка займає 3-4 рядки та легко сприймається;
   * Всі guard clauses на одному рівні - не потрібно тримати в голові стек умов;
   * Одразу зрозуміло, які перевірки виконуються та в якому порядку;
   * Додавання нової перевірки не вимагає створення нового рівня вкладеності.


3.5 Інструменти для рефакторингу


Для рефакторингу коду в екосистемі Node.js часто використовують ESLint, який аналізує код і пропонує способи автоматичного виправлення стилістичних та логічних помилок. Також ефективним середовищем є Visual Studio Code або WebStorm, що має вбудовані можливості для рефакторингу — перейменування змінних і функцій, виділення коду в окремі методи, автоматичне виправлення імпортів і форматування. Додатково, через розширення VS Code, можна інтегрувати ESLint, Prettier та інші утиліти, які допомагають підтримувати чистоту, узгодженість і якість коду під час рефакторингу.

4 ВИСНОВКИ


Рефакторинг є невід’ємною частиною процесу розробки програмного забезпечення, оскільки дозволяє підтримувати код у чистому, зрозумілому стані без зміни його функціональності. Регулярне застосування методів рефакторингу підвищує якість коду, зменшує кількість помилок, полегшує розширення проєкту та командну роботу.
Методи рефакторингу, такі як Replace Array with Object, Replace Exception with Test та Replace Nested Conditional with Guard Clauses, спрямовані на підвищення читабельності, зменшення складності логіки та уникнення антипатернів у коді.
Застосовувати рефакторинг слід у таких випадках:
   * після додавання нового функціоналу, щоб усунути дублювання або надмірну складність;
   * перед оптимізацією чи масштабуванням коду;
   * під час коду-рев’ю, коли виявлено ділянки з поганою структурою;
   * у процесі підтримки проєкту, коли код стає важким для розуміння.
